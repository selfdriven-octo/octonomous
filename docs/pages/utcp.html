No middleman. No one else to answer.

The Universal Tool Calling Protocol lets an agent read a manual and call a tool directly, over the protocol the tool already speaks. For an Octonomous Being, that removes a hop — and with it, a place where anyone else could check the call.

Abstract

Most tool protocols put a server between the agent and the tool. UTCP doesn't. It publishes a manual — a JSON description of each tool and how to call it — and then gets out of the way.

The agent calls the API, the command line or the stream directly, using the tool's own authentication. UTCP's designers name what that removes: the wrapper tax of building and running an adapter for every tool, and the security tax of re-implementing authentication inside one. Their principle is that an AI should be able to use any API a person can, with the same security as if a person had called it.

This note takes that seriously, from the Being's side. If nothing sits in the middle, nothing in the middle can check the call either. The API sees the Being's credential and treats the request as it would a person's. Every decision a wrapper might have made now has to be made by the Being — before it calls, in a form someone else can read.

It builds on Agents as Composers, which separated the model that writes a plan from the verified code that carries it out. Here, UTCP is a candidate for how that code gets called — and the question is what has to be true of a manual before a Being lets a composition depend on it.

Not
A protocol that makes tool calls safe
But
A manual that says how to call — and a Being that answers for the call
UTCP removes the middleman. Octonomous asks who is left answering.
01 — The protocol

A manual, then a direct call

UTCP is an open specification, at version 1.1, with client libraries in Python, TypeScript, Go and a growing list of other languages. Its centre is the manual: a document that lists tools and, for each one, the instructions for calling it over its native protocol.

find a manuala URL, a file, or an OpenAPI document
register its toolsname · description · input and output schemas
call the tool directlyHTTP · CLI · SSE · MCP · and more
native responsethe tool's own auth, limits and errors
↺ the protocol is only in the room for discovery
Manual
The tool list, plus utcp_version and manual_version. Served from a URL, read from a file, or converted from an existing OpenAPI document.
Tool
A name, a description, JSON Schema for inputs and outputs, optional tags, and an average response size so an agent can plan for what comes back.
Call template
How to reach the tool: a call_template_type — http, cli, sse, text, mcp and others — plus the fields that protocol needs.
Auth
Delegated to the native protocol. Secrets appear as ${VARIABLES} that the client resolves at call time, never written into the manual.
Plugins
Each protocol is a plugin. New call template types can be added without changing the core.

To continue the example from the companion notes — a community fund paying an electrician to repair the hall's switchboard — here is the vendor's booking API, described once, called directly:

{
  "manual_version": "1.2.0",
  "utcp_version": "1.1",
  "tools": [{
    "name": "book_job",
    "description": "Book an electrician for a quoted job",
    "inputs": { "type": "object",
                "properties": { "job_id": {...}, "date": {...} },
                "required": ["job_id", "date"] },
    "tool_call_template": {
      "call_template_type": "http",
      "url": "https://api.vendor.example/bookings",
      "http_method": "POST",
      "auth": { "auth_type": "api_key",
                "api_key": "${VENDOR_API_KEY}",
                "var_name": "X-Api-Key", "location": "header" }
    }
  }]
}

A UTCP manual with one tool · illustrative vendor · schema abbreviated

Version 1.1 added one field worth noting: allowed_communication_protocols. By default, a manual can only register tools that use its own protocol, so an HTTP manual can't quietly hand an agent a command-line tool. Widening that takes an explicit list. It's a small piece of restraint built into the protocol, and a good sign of its direction.

02 — Two shapes of tool calling

A manual, not a middleman

The contrast UTCP draws is with protocols that place a server between agent and tool. The Model Context Protocol is the common example: each tool is reached through an MCP server, which holds its own credentials, decides how to call the underlying API, and returns the result.

through a wrapper
Being ──▶ MCP server ──▶ API
          holds the credential · re-implements auth · a second hop

through a manual
Being ─ ─ reads manual (once)
Being ──────────────────▶ API
          native credential · native auth · one hop

Both shapes are legitimate, and they aren't exclusive — UTCP has an mcp call template, so an existing MCP server can sit in a manual like any other tool. The difference that matters here isn't latency. It's where a decision can be made.

Wrapper server
  • A place to enforce policy
  • Its own credentials and logs
  • One more thing to build and run
  • Trust moves to its operator
Manual + Being
  • Policy lives in the Being
  • Native credentials and logs
  • Nothing extra to run
  • The manual has to earn trust
Bespoke integration
  • Policy wherever the code put it
  • Credentials in the agent's code
  • Rewritten for every tool
  • Trust is whatever was last reviewed
03 — Responsibility

The Being at the door

A wrapper is overhead, and it is also a checkpoint. Whoever runs an MCP server can refuse certain arguments, log every call, rate-limit one agent and not another. Remove the server and those decisions don't disappear. They move — to the API, which only knows a credential, or to the Being, which knows why it is calling.

UTCP's design goal makes this explicit: the same security as if a person had called the tool. The API's checks are the ones built for people — authentication, authorisation, rate limits, billing. They answer whether this credential may do this. They were never meant to answer whether this particular call, made for this purpose, by this Being, is a good idea.

The API can check
  • Who holds the credential
  • What it is scoped to
  • How often it is used
  • Whether the request is well-formed
Only the Being can check
  • Why it is calling
  • Which facts the arguments came from
  • Who the effect will touch
  • Whether to call at all

This is the character as containment argument, arriving through a protocol. When nothing outside the Being stands between intent and effect, what the Being is — its identity, its constitution, its 4Cs — is the containment. Direct calling doesn't remove responsibility. It concentrates it.

No wrapper tax. No security tax. No one in the middle to answer instead.
04 — The gap

What a manual doesn't say

A UTCP manual is a good description of how to call something. It is not evidence of what that something is. Read against the verified and validated distinction, almost everything a Being needs before it binds a composition to a tool sits outside the manual.

A UTCP manual says
name · description
inputs · outputs · schemas
tags · average response size
call template · endpoint
auth type · ${VARIABLES}
manual_version
A Being also needs
who published it · identifier
digest · is this the one I trusted?
effects · what each tool touches
pre · post · checkable conditions
compensates · undo, if any
validation · evidence it behaves
status · active · revoked

UTCP's own documents are candid about this. The security guidance is strong on transport — HTTPS or WSS for every connection that isn't loopback, redirects re-checked at each hop, credentials never forwarded across origins, command-line execution treated as high risk. It doesn't describe signing or verifying a manual. And the RFC lists, as an open question, how clients should discover and trust new providers on the open internet.

TLS proves which domain served a manual. It doesn't prove the manual is the one that was reviewed, that it hasn't changed since, or that a tool called get_quote doesn't also write. The same URL can serve three different manuals in a week:

Mon
manual@4e1a · two tools · reviewed and trusted
Wed
manual@8b07 · same URL · adds cancel_job · not reviewed
Fri
manual@c3d9 · same URL · book_job now takes a deposit

An agent that trusts the URL calls whatever the URL serves today. A Being that trusts a digest notices on Wednesday.

A manual tells you how to call a tool. It can't tell you whether to trust it.
05 — A proposal

Wrap the manual, don't fork it

The tempting fix is to add fields to UTCP. The better one leaves the manual exactly as its publisher wrote it, and puts everything a Being needs into a separate, signed statement about it. Ordinary UTCP clients keep working. A Being reads both.

manual        hall-maintenance · plain UTCP 1.1 · unchanged
said          EKq8…4e1a   ← digest of the manual's own content

credential    ACDC · UTCP manual release
issuer        Vendor AID   · KERI-backed signature
subject       manual EKq8…4e1a
tools
  get_quote     effects read · external
  book_job      effects write · external
                pre   Quote ─accepted_by→ Fund
                post  booking.id present · booking.job_id = job_id
                compensates ← cancel_job
validation    suite EJr2…91c0 · 31/31
reviewed_by   Steward AID · Treasurer AID
status        active

Manual plus release credential · illustrative identifiers

Everything in the credential is checkable. The manual's digest either matches or doesn't. The issuer's identifier resolves through its key event log. Reviewers sign with their own identifiers, so a manual's provenance always includes someone other than its publisher. Revocation is a credential status, visible everywhere at once.

With the credential in place, a UTCP tool can become what the composers note calls a controller: a capability with a verified identity, declared effects, and contracts checked on every run. One difference remains. A controller in the composers note runs in the Being's sandbox; a UTCP tool runs behind someone else's API, where the Being can't inspect it. What the Being can do is verify who vouched for it, check its postconditions on every call, and stop trusting it the moment its status changes.

UTCP tool
A description of how to call something. Anyone can write one.
Controller
That description, plus an identity that vouches for it, effects it declares and contracts the Being checks. Somebody answers for it.
Composition
Which controllers, bound to which facts, this time. The Being answers for this.
A UTCP tool is a description. A controller is a commitment.
06 — Effects

Effects aren't in the verb

It's tempting to read effects off the call template: a GET reads, a POST writes, a text file is harmless. The protocol promises none of that. A GET can start a job; a command can do anything its process can; an MCP tool does whatever its server decides. So a Being starts from a pessimistic posture for each call template type, and moves off it only when a signed credential declares something narrower — and the declaration survives validation.

Call templateCan reachNarrowed byStarts as

customunknown until describeda signed declarationirreversible

A proposed default posture · not part of the UTCP specification

The Being's authority attaches to the class, not the tool's name, exactly as the composers note proposed for controllers:

readwriteexternalirreversible

Read freely. Write within scope. Act externally with a record. Do anything irreversible only with a principal or a quorum. A credential can move a tool down a class. Nothing a manual says on its own can.

07 — Secrets

A variable is a capability

UTCP keeps secrets out of manuals. A call template says ${VENDOR_API_KEY}; the client resolves it at call time from its configuration, the environment or a secrets service; and if a variable can't be resolved, the call fails rather than going ahead without it.

For a Being, that resolution step is the natural place for authority to bite. The secret isn't something the Being owns. It is something the Being is lent, for a purpose, under a delegation it can show:

${VENDOR_API_KEY}→delegated to this Being?→for this effect class?→governance passed?→resolve · call · forget

If any check fails, the variable stays unresolved and UTCP's own rule does the rest: the call doesn't happen. Failing closed on a missing secret is the protocol's default. It is also Chill — the most autonomous thing a Being can do is decline to act.

The lab runtime already reads secrets from AWS Secrets Manager by ARN. A UTCP loader would route variable resolution through the same path, after govern rather than at start-up, so a credential is in memory only for the call it was approved for.

08 — A custom call template

A door, not a wrapper

UTCP is extensible: a client can support call template types the specification doesn't list. That matters for tools that aren't on the open web at all. Postern, from the same organisation as Octonomous, is one: a single UDP port, a Noise_IK handshake that only enrolled keys can complete, and a short list of named operations granted per key. Strangers get silence — no error, no banner, nothing to discover.

Wrapping Postern in an HTTP service to make it agent-friendly would undo the point. A postern call template wouldn't. It describes the door and lets the Being knock with its own key:

tool                hall_board_status
call_template_type  postern
responder           203.0.113.7:51820
responder_key       ${HALL_RESPONDER_KEY}  ← distributed out of band
initiator           the Being's own enrolled key · never a variable
op                  status  · granted to this key, and nothing else
limits              args ≤ 512 bytes · plaintext ≤ 1024 bytes

Illustrative · no postern call template exists yet

Three things carry over, and each is worth keeping. Discovery doesn't happen on the network: a responder answers nobody it hasn't enrolled, so the manual travels the way the responder's public key does — out of band, from someone the Being already trusts. The manual's protocol allow-list contains postern and nothing else. And Postern states a limit that every UTCP integration should borrow: an authenticated message is not an authorised action. The channel proves who is speaking. Whether to act is decided above it.

Postern describes itself as a strong minimal design, not a proven most-resistant protocol. The same caution applies to anything built on it here.

Authentication proves who is calling. It was never meant to decide whether to call.
09 — Compose, check, call

Where UTCP sits in a composition

In the composers pattern, nothing moves until a whole score has been checked. UTCP changes how a step reaches the world, not whether it is checked first. The sequence gains one step at the front of verification:

01Compose a draft scoregenerative
02Verify each manual by digest and issuernew · verified
03Resolve each tool to a controllerverified
04Type-check bindings against the manual's schemasvalidated
05Ground every precondition in contextvalidated
06Authorise each effect classmay I
07Curious · Caring · Constructive · Chillshould I
08Approve the irreversible stepshuman
09Sign the compositioncommit

Then each step plays:

resolve secrets→check pre→call natively→check post→receipt

On Wednesday in the example above, step 02 fails: the URL serves manual@8b07, and the release credential names @4e1a. Nothing is booked. The composer either pins the manual it trusted or waits for a new release credential. When a step does run, the receipt names what the Being actually depended on — not a URL that may serve something else tomorrow:

receipt     fund-hall-repair · step 4
tool        book_job  via http POST
manual      EKq8…4e1a  · release credential EBn3…7d22
effects     write · external  · under delegation EFa0…
post        booking.id present ✓  booking.job_id = job_id ✓
signed      Being AID · KERI

10 — Character

Character reads the manual

Policy can check a manual's digest and a tool's effect class. Only character asks whether this Being should be calling this tool, for this purpose, right now.

CuriousWho published this manual, and is it the one that was reviewed? What does each tool actually touch — declared, not guessed from the verb?
CaringThe API will treat this call as a person's. Who is affected if it goes wrong — and do they know a Being is calling?
ConstructiveUse the tool as its owner built it — native auth, native limits — and leave a receipt that names exactly what was called.
ChillA manual with two hundred tools doesn't mean registering two hundred. Register the few the work needs. An unresolved variable is a reason to stop.
The manual lists what's possible. Character decides what's called.
11 — Inside the lab runtime

Next to MCP, keyed by digest

The Octonomous lab runtime already connects to MCP servers. Its MCP manager lists each server's tools and registers them in the same registry as local handlers, under names like mcp:server:tool, with each tool's input schema kept as metadata. Policy then checks the name against the Being's constitution and authority.

A UTCP loader fits the same shape, and is a smaller change than it sounds: read a manual, register its tools, call them directly. What the composers note asks of the registry applies here too:

             v1.0 MCP today              UTCP, composed
discover     server lists its tools      manual by URL, file or out of band
verify       —                           manual digest + release credential
register     mcp:server:tool, by name    utcp:manual@digest:tool
schema       stored as metadata          checked on every call
credential   token in server config      ${VAR} resolved after govern
call         through the MCP server      direct, native protocol
receipt      the event                   manual · tool · template · credential

None of this is shipped. Each line is a change to a piece that already exists — the registry, govern, the secrets path, the receipt — not a new runtime.

12 — Honest framing

What this note doesn't claim

This note does not
  • Claim UTCP is unsafe — or safe
  • Make a remote API inspectable
  • Replace MCP where a wrapper helps
  • Describe a published UTCP extension
This note does
  • Say where decisions go without a middleman
  • Separate a manual from trust in it
  • Leave the manual as its publisher wrote it
  • Show where UTCP lands in the runtime

UTCP is a sound idea. Most tools already have good interfaces, and wrapping each one again is expensive and often less secure than the original. Nothing here argues against it. A signed manual can still describe a buggy API, a declared effect can still be wrong, and a Being can still call the right tool for the wrong reason. The release credential, the effect postures and the postern call template are proposals in this note, not part of the UTCP specification.

Octonomous is a framework for what a being is, not a security appliance. Direct calling concentrates responsibility; this note is about making sure the Being is ready to carry it.

13 — Conclusion

Direct calls, answerable Beings

UTCP's bet is that agents should use tools the way people do: directly, through the interfaces those tools already have, under the security they already enforce. It's a good bet, and it puts the Being exactly where a person would stand — at the door, credential in hand, with nobody between it and what happens next.

a verified manual+declared effects+a Being that composes=a direct call someone can answer for
CuriousCaringConstructiveChill

Curious checks who wrote the manual. Caring remembers the API thinks a person is calling. Constructive uses the tool as it was built, and leaves a receipt. Chill registers only what the work needs — and stops when a secret won't resolve.

Not agents that call everything they can reach. Beings that answer for every call they make.
